# 獨立唯讀審查：434af1d 現用 `car.ino` / `rewrite_car.py`（HEAD e627004）

## 1. 結論與確定性邊界

我核對了 AGENTS.md、car.md、hardware.md、`docs/CURRENT_STATE_2026-10-25.zh-TW.md`，以及根目錄 `car.ino` 全檔、`tools/rewrite_car.py:240-319`、`tools/export_car.mjs` 和 `blockly_codegen.py` 的片段。先形成自己的發現後，才讀 squad 報告。

- **結論：** 目前程式有可證明的狀態交接錯誤，也有多條可達路徑能分別產生「慢速直衝」「同側重複反轉／過轉」「仍看到側線卻停車」和「寬白期間沒有期限的 100/100 前進」。
- **確定的部分：** 以下都是手動推演原始碼得到的可達路徑。
- **不確定的部分：** 沒有事故當時的 ADC/F/phase/馬達紀錄，也不知道車上韌體版本、轉彎幾何或實際輪速，所以無法判定哪一條就是現場事故的原因。物理白面不等於 F14，F bit 只代表 ADC<70。
- **未做的事：** 我沒有比對 XML 與 INO 的位元組，也沒有編譯；「`car.ino` 由 `car.xml` 匯出」是沿用文件的說法。

## 2. 依優先序排列的發現

### P1-A　RISK（屬於使用者政策沒有涵蓋的缺口，不是寫錯）：中心來源 150 ms 期限把有效轉彎變成直衝或停車

- **位置：** `car.ino:234-286`（rewrite:290-295）。
- **路徑一：右 60° 慢速直衝。**
  - 由 F2 確認入彎（`turnDirectionSource=0`），開始 150/-114 反轉。
  - 曾經 F0（已離線），但 150 ms 內還沒收線。
  - 到期時 F0：走 `loss_fallback`，`gapDirection=turnDirection`，命令 45/15 最多 120 ms。
  - 之後 `cross_gap` 每 120 ms 續期（`car.ino:503-550`），方向已過期，只剩 45/45 直行，直到 180 s 上限。
- **路徑二：仍看到側線卻停車。**
  - 到期當下若是 F2（右轉還沒離線，或 A2 下面是側邊白面）或 F8，條件 `car.ino:235` 不成立。
  - 結果 `turnFault=1`，執行 `stop2()`。
  - 兩個停用開關只涵蓋 F0/F14，所以「證據較強」的 F2 反而被鎖停，比完全失線（F0）更嚴重。
- **最小修正或決策：** 需要使用者決定 150 ms 到期時遇到 F2/F8 要怎麼處理（繼續轉到 800 ms、改成前進收線，或維持停車）。150 ms 到期時遇到 F0，要不要先繼續原方向反轉，而不是直接轉成 gap 爬行，也一樣要使用者決定。

### P1-B　BUG（確認 squad BUG-01）：完成轉彎後舊候選沒有作廢，會立刻再次反轉

- **位置：** `car.ino:305-309` 完成轉彎時沒有清 `turnCandidate/turnCandidateAt`；轉彎期間 `car.ino:1265` 擋住候選更新；`car.ino:1278-1287` 和 `1368` 直接沿用舊的起算時間。
- **路徑：**
  - 右轉在 F6 收線完成。
  - 下一個樣本是 F2，`turnCandidateElapsed` 已經遠大於 15 ms。
  - 立即再次進入右轉，命令 150/-114。
- **影響：** 這是同側重複反轉，比較能解釋過轉，不是轉錯邊。
- **修正：** 入彎和完成時都清掉候選。

### P1-C　RISK（新增，屬於設計後果）：寬白恢復期間持續 F14 沒有任何期限

- **位置：** `car.ino:1257` 只有在 `cornerWideRecovery==0` 時才會因 900 ms 逾時故障；`1548-1564` 方向過期後是 100/100。另外 `cross_gap` 遇到 F14 會立即交回主迴圈（`car.ino:566`）。
- **路徑：**
  - 已取得方向的寬白，或轉彎中出現 F14（`car.ino:222`）。
  - 120 ms 後變成 100/100 前進。
  - 只要 F14 不中斷，就一直前進到 180 s。
- **風險放大因素：** hardware.md:56、60 的舊量測顯示賽道外地板讀值 35～52，低於 70。若現況仍是這樣，衝出賽道後會維持 F14 並持續 100/100。這一點未經現況 ADC 驗證。
- **影響：** 對「60/90° 直衝」的解釋力強。
- **修正：** 恢復期間的寬白也要有界限，到期後要轉成某個停車或備援狀態，由使用者決定是哪一種。

### P2-A　BUG（新增）：收線後的失線備援用入彎方向，而不是最近的收線側

- **位置：** `car.ino:373-386`，共用 rewrite:254-259。收線階段 `turnActive==1`、`gapActive==0`，所以第二個分支 `gapDirection = turnDirection`，完全沒有參考 `turnCaptureSide`。
- **路徑：**
  - 右轉中由 F2 開始收線。
  - 中途 F0，60 ms 預算開始計時。
  - 線又出現在 F8（`side=-1`，命令 20/100 向左）。
  - 再次 F0：因為 `turnCaptureGapPending` 不會重設（`car.ino:367`），立即超過 60 ms。
  - 備援方向卻是 +1，命令 45/15 向右。
- **影響：** 能解釋轉錯邊，或過轉後越轉越遠。
- **修正：** 收線階段若 `turnCaptureSide≠0`，優先用它當備援方向。

### P2-B　RISK（新增）：小修正的證據被當成彎道方向，兩個時間窗也不一致

- **位置：** `car.ino:1277` 直線上的 F6/F12 也會寫入 `turnDirection`；`1317-1320` 寬白取得方向接受 250 ms 內的舊證據；但輸出 `1549` 只認 120 ms。
- **路徑一（轉錯邊）：**
  - 直線上 F6 持續 15 ms。
  - F4 不到 80 ms。
  - 接著遇到左彎寬白 F14。
  - 寬白被標成右，命令 100/50 偏右。
- **路徑二（有方向卻直行）：**
  - 證據已經 130～250 ms，仍會進入恢復狀態。
  - 但輸出時方向已過期，立刻 100/100。
  - 同時升降台／終點／逾時都被抑制。
- **修正：** 統一兩個時間窗；決定小修正的證據能不能拿來當彎道方向。

### P2-C　RISK（新增，註解顯示是刻意設計）：gap 遇到 F14 時方向資訊被丟掉

- **位置：** `car.ino:566-569` 交接時清掉 `turnDirection`；`gapDirection` 沒有傳給 `wideDirection`。
- **路徑：**
  - 失線備援中遇到彎道寬白。
  - 主迴圈寬白取得方向失敗（`car.ino:1312-1321`）。
  - 命令變成 45/45；F14 滿 30 ms 就建立升降台候選（`car.ino:1182-1196`）。
  - 下一個樣本若是 F4 且外側無提示，就停等 23.35 s。
  - 若已經過了升降台，F14 滿 250 ms 就判終點（`car.ino:1259`）。
- **說明：** 註解寫著「Wide line returns to marker handling」，顯示這是刻意設計，但彎道與十字共用同一條路徑。
- **決策：** 需要使用者決定 gap 交給寬白時，能不能保留已取得的方向。

### P2-D　RISK（推論，依賴實際車速）：快速通過側線時方向沒有確認就失線

- **位置：** `car.ino:1273/1284`、`1513`、`1524-1530`。
- **路徑：**
  - 230 PWM 下 F6→F2 總共不到 15 ms 就變成 F0。
  - 方向還沒確認，`turnDirection` 為 0。
  - 進入 0 方向 gap，命令 45/45。
  - 如果 A1 沒有在 20 ms 內確認，就會直衝。
- **說明：** 這是真實可達的程式路徑，但會不會實際發生，取決於還沒量測的車速和側線通過時間。

### P2-E　BUG（確認 squad BUG-02，但我認為它是低優先）

- **位置：** `car.ino:225` 先用舊方向計算可收線資格，`230` 才用外側證據覆寫方向。
- **我的看法：** 順序不一致是真的，但後果是「沿著目前中心看得到的線收線」。在兩邊證據互相衝突時，這不一定比改向更差，所以不支持列為高優先。

### P3

- **收線後 60 ms 失線預算不會重設：** `car.ino:367` 只在入彎時清。第二次短暫失線會立即走備援。這和「固定預算」的設計一致，但會放大 P2-A。
- **註解與程式不一致，且有死碼：**
  - 註解 `car.ino:211` 說「Active-turn F14 … share 60ms」，但收線前遇到 F14（`449-460`）並沒有這個預算。
  - `car.ino:310-314`、`320-324` 的 F8/F2 分支在完成條件下不可能執行。
  - `car.ino:444` 實際上被 F10 split 判斷先攔截，到不了。
- **診斷資訊不足：** `DEBUG_SERIAL=0`，序列輸出只有 ADC/F（`car.ino:1639-1650`）。LED 藍色同時代表外側探查停車、升降台等待、故障和終點（`car.ino:721`），無法從 LED 分辨是誰造成停車。
- **未驗證的物理假設：** `TURN_MIN_MS=30` 的盲區，加上收線前不接受反側單顆（`car.ino:225`），再加上反轉 800 ms 期限（外側來源），可能把線轉過頭、轉到 180°。沒有轉速資料，只列為假設。

## 3. 既有問題、潛在問題與排除的假設

- **既有問題（目前程式就會發生，原始碼可證明）：** P1-B、P2-A、P2-E 是實作錯誤；P1-A、P1-C、P2-B、P2-C 是確定的程式行為。
- **使用者政策的後果（不是寫錯）：**
  - `LOSS_STOP_ENABLED=0` 讓失線變成無限續期的 45/45 爬行（`car.ino:503-550`）。
  - 30 ms 寬白後接 F4 就停等升降台，彎道上會有假陽性。
  - 升降台之後的終點判定。
  - 230/174 的速度上限。
- **只能推論的部分：** P2-D、180° 過轉、地板讀值造成 F14。
- **排除的假設：**
  - 馬達極性或左右對調：左右分支互相對稱，和 hardware.md:31-32 一致，沒有證據。
  - 匯出器缺陷：`export_car.mjs:27-34` 只核對父積木，沒有核對輸入名稱。這是驗證範圍有限，不是已發現的缺陷。
  - 整數溢位：數值都很小。
  - SRAM/flash 不足：沒有建置資料，不作宣稱。
  - `car.ino:1633` 的「未歸類圖樣」停車：實際上不可達。
- **與 v0.4.0 比較的限制：** v0.4.0 只是發布分類，從來沒有完成整圈的實車驗收，所以「回退到 v0.4.0」不能當成穩定基準。

## 4. 對 squad 報告的評估

- **BUG-01：同意。** 我把影響修正為同側重複反轉、過轉，而不是轉錯邊。

- **R-02、R-04、R-06、R-08：同意。** 我自己核對 `car.ino:1155` 也確認：單次 F2/F8 會立即把直道速度階段重設回 100。
- **R-03、R-05：同意，但缺了重點。** squad 沒有指出持續 F14 的恢復狀態完全沒有期限（P1-C），也沒有指出 250/120 ms 兩個時間窗不一致。
- **我新增的發現：** P1-C、P2-A（新的 BUG）、P2-B、P2-C、P2-D，以及 60 ms 預算、死碼、註解不一致。

## 5. 建議修復順序（只排順序，不實作）

1. 修兩個能明確修好的 BUG：P1-B（入彎和完成時作廢候選）、P2-A（收線階段的備援用 `turnCaptureSide`）。
2. 請使用者決定：P1-A 的 150 ms 到期時，F2/F8 和 F0 各要怎麼處理；P1-C 的恢復期間寬白要不要設期限。
3. 統一方向時間窗，決定小修正證據能不能當彎道方向（P2-B）；決定 gap 交給寬白時是否保留方向（P2-C）。
4. 順手修 P2-E 的順序問題，並清理死碼和不一致的註解。
5. 以後要採集資料時，先加上 phase 和停車來源（stop owner）的輸出欄位。本輪不啟動採集，也不新增測試。
