## 一、確定實作缺陷

### BUG-01：完成轉彎後，舊方向候選能立即重啟反轉（高優先）

來源：tools/rewrite_car.py:244-245、450-456、480-485、561-610。begin_turn與done都未清除turnCandidate／turnCandidateAt，且轉彎期間候選更新被turnActive條件擋住。

| 時間 | 觀測與狀態 | 可達命令 |
|---|---|---|
| -15 ms | F2建立右候選，無外側證據 | 一般右差速 |
| 0 ms | F2滿15 ms，進右尖角 | 左150、右反轉114 |
| 30 ms | F4開始收線 | 100／100 |
| 45 ms | F4滿15 ms，完成轉彎 | turnActive清0，但右候選與舊起點仍在 |
| 50 ms | 單次F2 | 候選仍同側，elapsed按舊起點計算，立即再次反轉，沒有新的15 ms確認 |

這會讓完成後的一次側線樣本再次觸發強轉向，具有造成反覆轉向／過轉的路徑。是否對應實車180度那次仍無事件資料。

建議修法：明確區分已消耗候選與新事件，在入彎／完成／取消時失效舊候選；新入彎資格必須重新累積。不是把15 ms改得更長。

### BUG-02：先算回線資格，再覆寫方向，當圈可沿舊側收線（高優先）

來源：tools/rewrite_car.py:240-243、283-303；live car.ino:225-234亦保留相同順序。turnCaptureVisible在外側方向覆寫之前計算。

手推：原本右轉，10 ms時曾F0；40 ms時F2、且外側左方向已確認。先按舊右方向把F2判為可回線，再把turnDirection改為左，隨後仍令turnCaptureStarted=1，依F2輸出左100／右20前進。從這時起單側F2又因captureStarted而持續有效，無法由新方向資格檢查阻止。

這是方向來源與回線資格的同圈不一致；並非已證明馬達接線反了。反方向完全對稱。

建議修法：先完成方向選擇／修正，再計算可回線；方向改變時明確處理舊的capture／confirm狀態，避免混用兩個方向的證據。

## 三、感測與硬體部門：缺的是這一場賽道的對照

1. hardware.md:50-61的舊測量稱線上ADC約35，地板也35～52，所謂「全黑」386～540；當前F仍以小於70在線。這份紀錄不能證明目前白線賽道的極性、感測高度與各顆門檻。不能把肉眼「全白」直接改成F14或F0的策略。
2. 外側右證據要求A1<70且A5≥120（rewrite:467-470），不是只要右側看到某物就能確認；若A1=60／A5=100，即使現場像是右出口，也不提供右候選。門檻與通道對比未對這次環境校正。
3. 普通F只保留中間三顆位置。F14時不建立新外側方向（465-474），白色寬面／十字／相鄰線可能產生相同編碼。這是觀測歧義，不能靠再多一組F值表唯一破解。
4. 舊接線文件記錄左右馬達／前進電位曾確認，**沒有證據支持現在直接交換馬達或全域左右顛倒**。

這些均列為高風險與待釐清證據，不宣稱已找到實際感測器極性接反或機構故障。

## 四、匯出與版本部門

- 沒找到新的、可證明的現行XML／Arduino匯出語義錯誤。Boolean與數字0比較造成接點拆開的舊問題，已用turnCaptureVisible整數修正；不再列為現行根因。
- export_car.mjs:23-40核對匯入接點及generator存在，**不等於編譯、函式庫、資源與實車行為驗證**。現行car.ino使用moto_NeoPixel；舊temporal候選的core-only編譯／RAM數據不能沿用。沒有建置資料，不能宣稱Nano記憶體溢位。
- 本機目前car.xml／car.ino與存檔一致；車上實際版本仍未知。不能將「來源更新完成」當成「該版已燒錄並行駛」。
- v0.4.0是正式Release，不是已測完整一圈的穩定性基準；回退可以回復程式，不能保證回復實車穩定。
- CONTROL_POLICY、FIELD_TEST、LIVE_CAPTURE仍描述保留的temporal候選、上限100與18欄CSV；目前主檔使用另一格式與控制工具。現況文件已有優先序，但舊入口仍可能讓人套錯流程。這是文件適用範圍風險，未證明已在現場發生。

## 五、為何修改後問題反覆出現

先前修改依口語症狀，依序改入彎、回線、停車、F14反轉，再因「仍掃到側線」澄清撤回反轉；當時沒有同次rawADC／F／phase／命令序列，改動可能沒有作用在真正失敗分支。

我先前將多個局部修補當成下一個解法，卻沒有先把不同階段的證據與輸出契約統一起來；本次審查確認這會留下交接矛盾。這是分析與實作方法的問題，不能歸咎於使用者不加測試的要求。

目前「不再停車」可只是變成45／45往前，「方向保留」可只是變數仍在但命令已回同速，「仍看到線」也可能不滿足capture狀態接受的線型。這些是不同層次，不能用一項參數同時修好。

## 六、建議處理順序（本輪未套用）

1. **先修2個確定實作缺陷**：方向先決後判回線；入彎／完成消耗舊候選，確保新事件重新資格確認。
2. **統一狀態契約**：明確列出可見線前進、實際失線搜尋、收線、寬白穿越與關卡停車各自能接受哪些證據、如何交接。先解決F2持續與早入彎期限，不再靠多個零散if補丁。
3. **保留使用者已選開關與速度作基準**，不要擅自恢復鎖停或再提高彎速；累積失線預算／恢復清除／十字判斷若需改語義，應作獨立可審查的策略變更。
4. **補最小可觀測性設計**：一個事件ID對應韌體版本、raw A1～A5、F、phase、direction/source、candidate、capture、gap、wide recovery、lift／finish／fault owner與實際左右命令。此處只提出欄位，沒有啟動採集或要求重新跑賽道。
5. 日後若取得事件資料，再決定感測門檻、入彎速度、輪速／角度需求；Arduino編譯、燒錄身分及實車驗收分開記錄，不用匯出成功代替它們。
